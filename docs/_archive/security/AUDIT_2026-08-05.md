# Auditoria de Segurança — Teglion (somente leitura)

**Data:** 2026-08-05
**Escopo:** repositório completo (`frontend/`, `backend/`, `supabase/`, CI, configs de produção) + histórico Git (83 commits, todas as branches)
**Método:** revisão estática de código, configuração e histórico Git. Nenhuma alteração de código/dados foi feita. Nenhum teste destrutivo foi executado contra produção.
**Nota sobre segredos:** valores reais de credenciais encontrados foram **redigidos** neste relatório. Onde um segredo real foi identificado, isso é indicado sem reproduzir o valor.

---

## Resumo executivo

O Teglion já tem uma base de segurança bem acima da média para um piloto: CSRF double-submit, CORS com allowlist estrita, cookies httpOnly, hashing Argon2id, lockout de login persistido em BD, verificação de assinatura no webhook Stripe, sanitização de logs e de respostas JSON, scan de segredos e testes de isolamento multi-tenant já documentados (`TENANT_ISOLATION_REPORT.md`, veredito "aprovado"). Isso já é implementado — não é trabalho a refazer.

O achado mais grave não está no código nem no Git: são **credenciais de produção reais (live) guardadas em texto simples num ficheiro local** (`backend/.env.local`), incluindo a chave `service_role` do Supabase, segredos JWT, chave secreta Stripe **live**, chave Brevo, credenciais Redis, segredo OAuth Google e chave VAPID. Esse ficheiro nunca foi commitado (confirmei isso no histórico completo do Git), mas continua a ser o risco nº 1 agora, porque esses valores já foram lidos nesta sessão de auditoria e, se esta pasta alguma vez sincronizar para nuvem (iCloud/Dropbox), for copiada, ou o portátil for comprometido, é o comprometimento total da produção.

O segundo risco estrutural é conhecido e já auto-documentado pela equipa: o isolamento multi-tenant depende inteiramente da camada de aplicação (`firm_id` em cada query), porque o backend usa a `service_role` do Supabase, que **ignora RLS**. As políticas RLS existem no schema mas não protegem o tráfego real da API. Isto é um risco aceite e monitorizado (testes de isolamento), mas é uma superfície de falha única: um novo endpoint sem `.eq('firm_id', ...)` é um vazamento cross-tenant sem rede de segurança no banco.

## Achados por criticidade

### 🔴 CRÍTICO

#### C1 — Segredos de produção reais em texto plano em ficheiro local
**Onde:** `backend/.env` e `backend/.env.local`
**O quê:** os dois ficheiros contêm, em texto simples, credenciais **live** de produção: `SUPABASE_SERVICE_ROLE_KEY`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `DATA_ENCRYPTION_KEY`, `DOCUMENTS_SIGNING_SECRET`, `BREVO_API_KEY`, `STRIPE_SECRET_KEY` (prefixo `sk_live_`), `STRIPE_WEBHOOK_SECRET`, `REDIS_URL` (com password embutida), `GOOGLE_OAUTH_CLIENT_SECRET`, `VAPID_PRIVATE_KEY`, e uma `LEGACY_CRYPTO_PASSPHRASE` fixa e previsível.

**Risco:** posse destes valores equivale a comprometimento total: acesso ilimitado ao banco (bypass de RLS via service role), capacidade de forjar tokens JWT de qualquer utilizador/escritório, decifrar dados sensíveis cifrados em BD, movimentar dinheiro/reembolsos via Stripe e ler dados de pagamento de clientes, enviar email/SMS como a empresa, e enviar push notifications a todos os utilizadores. Confirmei que estes ficheiros **nunca foram commitados** (`git log --all` nos 83 commits não mostra `.env*` nem os padrões de segredo com valores reais — apenas placeholders de teste e exemplos de documentação) e que estão corretamente listados em `.gitignore`. Ainda assim, ficheiros locais não geridos por um cofre são o vetor nº 1 de fuga em incidentes reais (backup, sync de nuvem, laptop roubado, cópia acidental).
Como esta auditoria (executada por um agente de IA) leu o conteúdo destes ficheiros, deve tratá-los como **potencialmente expostos** a partir de agora.

**Correção:**
1. Rodar **imediatamente** todos os segredos acima: chave Stripe live + webhook secret, `SUPABASE_SERVICE_ROLE_KEY`, `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` (isto invalida sessões ativas — esperado e aceitável), `BREVO_API_KEY`, `GOOGLE_OAUTH_CLIENT_SECRET`, `VAPID_PRIVATE_KEY`/`VAPID_PUBLIC_KEY`, password do Redis.
2. `DATA_ENCRYPTION_KEY` precisa de plano de rotação cuidadoso (reencriptar dados existentes antes de invalidar a chave antiga) — não rodar às cegas.
3. Nunca guardar segredos de produção em ficheiros locais. Usar as variáveis de ambiente do Render/Vercel para produção (já é o caso, aparentemente) e, para desenvolvimento local, usar apenas valores de teste/dummy — nunca copiar valores `live` para a máquina de um developer.
4. Verificar se a pasta `Documents/TeglionApp` sincroniza com iCloud Drive, Dropbox ou similar no Mac deste developer; se sim, os segredos já podem ter saído da máquina.
5. Considerar um cofre de segredos (1Password, Doppler, Vault) para acesso local quando for mesmo necessário testar contra configuração real.

### 🟠 ALTO

#### A1 — Isolamento multi-tenant sem rede de segurança no banco (RLS ineficaz para o tráfego real)
**Onde:** `supabase/rls.sql`, `supabase/policies.sql` vs. uso de `SUPABASE_SERVICE_ROLE_KEY` em todo o backend.
**O quê:** as políticas RLS existem e estão bem desenhadas (`firm_id = current_firm_id()`), mas o backend acede ao Supabase exclusivamente com a `service_role`, que **ignora RLS por definição**. A proteção real de isolamento multi-tenant hoje é 100% aplicacional: cada repositório precisa de incluir `.eq('firm_id', firmId)` manualmente. Isto já está a ser feito de forma consistente (confirmei ~144 ocorrências de `.eq('firm_id', ...)` em 33 ficheiros, e há teste dedicado `tenant-isolation-test.js` com veredito "aprovado" em `TENANT_ISOLATION_REPORT.md`) — mas é a própria equipa que classifica isto como risco residual "Alto" em `docs/security/SECURITY.md`.

**Risco:** um único endpoint novo, ou uma refatoração, que esqueça o filtro `firm_id` é um vazamento de dados cross-tenant silencioso — sem qualquer bloqueio do banco de dados para travar o erro.

**Correção:**
1. Confirmado: `npm run test:tenant-isolation` **não corre no CI** (`.github/workflows/ci.yml` só chama `test:security-static`, não `test:security`, que é quem inclui o teste de isolamento). Adicionar este teste ao pipeline de CI, pelo menos em PRs que tocam `backend/src/**`.
2. Avaliar a Fase 7 já planeada: emitir JWTs compatíveis com `auth.jwt()` do Supabase (ou usar `SET request.jwt.claims`) para que o RLS realmente proteja consultas feitas com um role menos privilegiado, deixando `service_role` só para operações administrativas específicas.
3. Curto prazo: criar um linter/regra de code review que bloqueia merge de qualquer novo `.from(...)` sem `.eq('firm_id', ...)` correspondente (script simples de grep no CI já seria uma rede de segurança barata).

#### A2 — Rate limiting "fail-open" quando o Redis cai
**Onde:** `backend/src/utils/rate-limit-store.js`
**O quê:** se o Redis ficar indisponível durante a operação, `safeSendCommand` devolve respostas fabricadas (`INCR → 1`, `PTTL → 60000`) que fazem o `express-rate-limit` global **nunca bloquear** pedidos. Isto é uma decisão de design deliberada ("fail-open: não bloqueia pedidos") para não derrubar o serviço, mas significa que exatamente durante uma instabilidade (quando o sistema está mais vulnerável) o rate limiting global fica efetivamente desligado.
**Nota:** o lockout de login por força bruta é independente disto (guardado em BD via `login-attempts.repository`), então login continua protegido mesmo com Redis em baixo — isto mitiga bastante o risco.

**Risco:** abuso/scraping/DoS de baixo esforço em rotas não cobertas pelo lockout de login durante uma janela de indisponibilidade do Redis.

**Correção:**
1. Emitir alerta operacional (Sentry/Slack) sempre que `markRedisUnavailable` é acionado em produção, para resposta rápida da equipa — hoje só há log.
2. Avaliar fail-closed (ou um limite mais restritivo local em memória como fallback) especificamente para rotas sensíveis não cobertas por outro controlo.

### 🟡 MÉDIO

#### M1 — Sanitização de logs não é aplicada de forma consistente
**Onde:** `backend/src/utils/logger.js`, `backend/src/middlewares/log-sanitization.middleware.js`, `backend/src/server.js`
**O quê:** existe um `logger.safe.*` (sanitiza PII, tokens, chaves Stripe, JWTs, etc. antes de logar) e é usado em vários pontos — mas os handlers globais `unhandledRejection`/`uncaughtException` em `server.js`, entre outros, chamam o `logger.error`/`logger.warn` **direto** (não `logger.safe`), passando `stack`/`message` sem sanitização.

**Risco:** se uma exceção não tratada contiver PII ou um fragmento de segredo na mensagem (ex.: erro de biblioteca que ecoa parte de uma connection string ou input do utilizador), isso vai parar sem redação no stdout/serviço de logs (Render) ou no Sentry.

**Correção:** padronizar todo logging de erro/aviso para passar por `logger.safe`, ou (mais robusto) mover a sanitização para dentro do formatter do Winston, para que se aplique a qualquer chamada, independentemente de disciplina no call site.

#### M2 — Teste de isolamento multi-tenant não é obrigatório no CI
Já descrito em A1, mas registo aqui a ação concreta separada: hoje é execução manual/semanal. Ver correção 1 de A1.

#### M3 — Migração de `crypto-js` legado incompleta
**Onde:** `backend/src/utils/safe-display-text.js`, variável `LEGACY_CRYPTO_PASSPHRASE`
**O quê:** ainda existe um caminho de decifragem legado via `crypto-js` com uma passphrase fixa e de baixa entropia (padrão previsível tipo `<produto>-legacy-v<n>-secret-<ano>`), usado só como fallback para dados antigos que ainda não foram migrados para o esquema `enc:v1` (AES-256-GCM com `DATA_ENCRYPTION_KEY`). Já está identificado como dívida técnica em `docs/security/SECURITY.md` ("🔴 migrar para crypto nativo").
**Risco:** menor que os itens acima porque é só fallback de leitura, mas a passphrase fraca reduz a segurança de qualquer dado antigo ainda nesse formato.
**Correção:** concluir a migração dos dados legados para `enc:v1`/AES-256-GCM e remover o caminho `crypto-js` e a passphrase fixa.

#### M4 — CSP do backend permite `'unsafe-inline'` em `script-src`
**Onde:** `backend/src/app.js` (Helmet)
**Risco:** baixo hoje porque o backend é essencialmente uma API JSON, mas se algum endpoint algum dia servir HTML com input de utilizador, `'unsafe-inline'` remove a principal barreira contra XSS refletido.
**Correção:** remover `'unsafe-inline'` do CSP do backend se não houver necessidade real (confirmar se algum endpoint depende disso); caso contrário, migrar para nonce-based CSP.

### 🟢 BAIXO / observações

- **CSP do frontend** (`frontend/vercel.json`) inclui `https://*.supabase.co` em `connect-src`, mas não encontrei nenhuma chamada direta ao Supabase no código do frontend (a app fala só com o backend próprio — bom padrão, "zero trust" no frontend). Recomendo remover essa entrada se for mesmo não utilizada, para reduzir superfície.
- `exposedHeaders: ['Set-Cookie']` na config de CORS do backend é inofensivo mas inútil (browsers não expõem `Set-Cookie` a JS de qualquer forma); pode ser removido por clareza.
- Falta um `.env.example` versionado — já listado como risco residual "Baixo" pela própria equipa em `SECURITY.md`. Adicionar um, sem valores reais, reduz a tentação de copiar `.env` de produção para uso local.
- Não existe cadência documentada de rotação de segredos. Dada a descoberta de C1, recomendo definir uma política formal (ex.: rotação trimestral de chaves de API/JWT, imediata after qualquer suspeita de exposição).

## O que já está bem implementado (não precisa de correção)

Para dar o contexto completo e evitar retrabalho desnecessário:

- **Autenticação:** JWT em cookies `httpOnly` + `Secure` (nunca em `localStorage`), access token de 15 min, refresh token de 30 dias com rotação e `jti` rastreado em `auth_refresh_sessions`, hashing de password com Argon2id (com migração transparente de bcrypt legado), política de password forte, mensagens anti-enumeração, lockout de força bruta persistido em BD (5 falhas / 15 min, com delay progressivo) — independente do Redis.
- **CSRF:** double-submit cookie + header, comparação `timingSafeEqual`, validação de `Origin`/`Referer` contra allowlist, tratamento cuidadoso de casos WebView/Safari sem quebrar segurança.
- **CORS:** allowlist explícita por ambiente, sem wildcard em produção, `credentials: true` só com origem validada, rotas públicas restringem POST a origens conhecidas.
- **Autorização/RBAC:** `requirePermission`/`requireRole` aplicados de forma consistente; middlewares legados (`requireConsultantForClient`/`requireConsultantOwnership`) confirmei que são no-ops **não usados** em nenhuma rota ativa — não são um bypass real.
- **BOLA/IDOR:** padrão consistente de verificar `firm_id`/`client_id` do JWT contra o recurso pedido (ex. `findDocumentForActor`), devolvendo 404 (não 200 nem 403 informativo) em tentativas cross-tenant, evitando enumeração de existência de recursos.
- **Exposição de dados:** middleware `responseSanitizeMiddleware` remove campos como `password`, `passwordHash`, `refreshToken`, `secret`, `apiKey` de **toda** resposta JSON como rede de segurança adicional; payload de `/auth/me` é uma allowlist explícita (`toPublicAuthUser`), não um dump de linha de BD.
- **Webhooks:** assinatura do Stripe validada via `stripe.webhooks.constructEvent` antes de processar qualquer evento.
- **Headers de segurança:** Helmet no backend; no frontend (`vercel.json`), HSTS, `X-Frame-Options: DENY`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` e CSP explícitos.
- **Git/segredos no histórico:** varri os 83 commits de todas as branches por padrões de chaves reais (Stripe, Brevo, Google, Supabase, JWT, Redis) — **nenhum segredo real encontrado**, apenas placeholders de teste (`test-access-secret-min-32-chars!!`) e exemplos de documentação (`sk_live_...` como texto ilustrativo). `.env*` nunca foi commitado em nenhum momento do histórico.
- **CI:** `security:secrets` (scan de segredos) e `test:security-static` correm em todo PR/push para `main`/`staging`.
